# Conversation tab: composer controls, chat/terminal switching, and reading enhancements

Three features ship together here. The composer gains queuing, stashing, interrupt-and-send, double-Escape stop, and expand mode. The view gets a chat/terminal toggle and a model/effort pill. The turn bubble gets a ⋯ action menu, text-selection Reply overlay, and a view-mode dropdown that controls how much tool work is visible. Supporting infrastructure (a new `ChatWorkbench` component, `SessionDeleteDialog`, and a full `chatExtras` utility module) also lands in the same diff.

Watch for: **`handleStop` and the model pill are confirmed stubs** — pressing Escape twice or clicking the pill logs to console and does nothing. `onRewind` and `onFork` are **confirmed dead props** in the plain-turn path: they are declared on `ConversationTurnBubble` but never passed from `ConversationsPrimaryView`. `onReply` is **confirmed dead** in `ConversationChatThread`: the prop is accepted and immediately aliased to `_onReply`, making Reply non-functional in the rich-chat path. The view dropdown has **no click-outside handler** (confirmed), so it can be left open accidentally.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The composer change is the most self-contained of the three features. The Ctrl+G expand toggle attaches a window-level listener, which is unusual for a component-local concern and means every mounted instance of the composer would fight over that shortcut if more than one is rendered simultaneously.

The chat/terminal toggle and model pill are mostly infrastructure placeholders. The toggle works at the UI level, and the per-session `TerminalChatPane` embed is correctly gated behind the mode flag. The model pill displays a provider name read from local preferences but has no interaction logic — clicking it logs a warning. The `handleStop` stub similarly fires a console warn and does nothing, so users who double-Escape while an agent is running will see no effect.

The reading enhancements are split across two components. `onRewind` and `onFork` are never passed to `ConversationTurnBubble` from the parent view, so those menu items are silent. In `ConversationChatThread`, `onReply` is accepted and immediately discarded with an underscore prefix, so the Reply-on-selection button in the rich-chat path never fires the handler.

The `ChatWorkbench` component is a large new surface. The side-chat feature forwards messages directly via `sendChannelMessage`, prefixing them with a `[Side chat from ...]` annotation. That prefix is not stripped on the receiving end by any code visible in this diff, so the annotation will appear verbatim in the recipient agent's context.

<summary>Details</summary>

## `handleStop` and model pill stubs

`ConversationsPrimaryView.handleStop` (line 419) calls `console.warn("Agent stop not yet implemented")`. The hint bar now reads "Esc×2 to stop", and the user-facing docs describe it as stopping the agent. Users who rely on this shortcut during a long run will get no feedback. The model pill at line 721 similarly warns in the console when clicked — its tooltip says "Option+P / Alt+P to switch model", making it appear functional.

## `onRewind`, `onFork`, and `onReply` dead props

`ConversationTurnBubble` (confirmed) renders "Rewind to here" and "Fork from here" only when these props are non-null. `ConversationsPrimaryView` passes `onReply={handleReply}` to each bubble but passes neither `onRewind` nor `onFork`, so those menu items never appear.

`ConversationChatThread` accepts `onReply` but prefixes it `_onReply` and forwards it nowhere — not to `AgentTurn`, not to the user turn `<li>`. The selection overlay Reply button in the rich-chat path is therefore silent.

## Ctrl+G scope: window listener from a component

The Ctrl+G expand toggle in `ConversationComposer` registers a `window` keydown listener, not a local `onKeyDown`. The guard logic correctly passes through when the focus is on the composer's own textarea and skips all other editable elements. Where this breaks is if two instances of `ConversationComposer` are mounted at once (the `TerminalChatPane` chat view has its own composer, and `ConversationsPrimaryView` has another). Both would call `setIsExpanded` on themselves independently, so the toggle would fire twice on the same keystroke — once per instance. This is **likely** given the current rendering topology; it isn't tested.

## View dropdown click-outside gap

`isViewDropdownOpen` (confirmed) has no document-level `mousedown` handler. The dropdown is closed only by clicking one of its own options. Clicking the page content, another button, or the terminal pane leaves it floating open. The ⋯ action menu in `ConversationTurnBubble` already uses `document.addEventListener("mousedown", ...)` for this — the same pattern is absent from the view trigger.

## `externalDraft` / `restoreDraft` re-mount cycle

When a stash is restored, `restoreDraft` is set and `ConversationComposer` is re-keyed (`key={selectedSession.sessionId}:${restoreDraft ?? ""}`), mounting fresh with `externalDraft` set to the stash text. After the user edits the textarea, `restoreDraft` stays non-null in the parent indefinitely. If the session changes and comes back, `restoreDraft` would still be set and would force the stash text into the composer again. **Possible** — worth verifying that `restoreDraft` is cleared on `selectedSessionId` change.

## Side-chat prefix injection

`ChatWorkbench.ask` sends `[Side chat from {session.terminalId}]: {text}` to the target agent via `sendChannelMessage`. This arrives verbatim in the agent's context — nothing in this diff strips it. If this is infrastructure framing rather than intentional agent instruction, it needs server-side processing; if it is intentional, it should be documented. **Confirmed** by reading `ChatWorkbench.tsx`.

## Test coverage gaps

Not tested:

- Double-Escape stop (the most critical absent test given the stub)
- `onRewind` and `onFork` being wired from `ConversationsPrimaryView` through to the bubble
- The `onReply` path in `ConversationChatThread` (the underscore discard is not caught)
- Two `ConversationComposer` instances mounted simultaneously and the Ctrl+G conflict
- View dropdown dismissal on outside click
- The `restoreDraft` lifecycle when the session changes

The Alt+G toggle test fires a `keydown` event and checks the counter, not that the view switches — it covers the event binding but not the behavior.
